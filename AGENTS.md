# Правила ИИ-агента: доработка конфигурации 1С в расширении

Правила на каждый ход. Они сильнее «так быстрее» и сильнее привычек агента. Карта папок — `README.md`. Первый запуск —
`docs/08_Первый_запуск.md`.

Пять принципов. Ниже по файлу — те же принципы в виде запретов и порядка работы.

1. Дорабатываем конфигурацию только расширением.
2. Факты о базе — из живого MCP. Своя база в примерах другого проекта не описана.
3. Поставка — проверенный файл из Конфигуратора, не слова «сырцы обновлены».
4. Чужое не менять: другие проекты, чужие процессы, имя чата.
5. Не утверждать сделанное без проверки.

Имена объектов, порты и пути прошлой базы в `docs/` — пример процесса, не факты этой базы. Состав своей базы узнавать
из MCP (индексатор, граф) и из живой базы (`tests/smoke/bsl/config_info.bsl`).

Набор comol/ai_rules_1c (`rules\`, `skills\`, закрепление в `docs/08`) уточняет, как делать вид работы. Где он расходится
с этим файлом в части MCP, скриптов базы, сборки и запретов ниже — действует этот файл. История, почему правило
появилось, — `docs/06_Как_ставились_правила.md`, не этот текст.

## 1. Жесткие ограничения (без исключений)

1. **Метаданные — только через живой MCP** (индексатор кода, граф). Не фантазировать, не читать XML `conf`/`ext`
   целиком «вместо индекса», если объект уже в индексе. Исключение — файлы, которых еще нет в индексе (новые, только
   что выгруженные), и исходники внешних обработок `build/*/src`. MCP мертв → сказать прямо «MCP мертв» и **остановить**
   работу с метаданными, не продолжать по памяти.
2. **Объекты метаданных агент создает и правит сам**:
   справочники, документы, реквизиты, табличные части, регистры, роли, подсистемы, перечисления, заимствования — навыком
   comol `1c-metadata-manage` (или субагентом `1c-metadata-manager`), с проверкой XML после правки (`meta-validate` /
   `cfe-validate`, проверка UUID). XML метаданных руками мимо навыка не править, каталог объекта не копировать.
   Действуют п. 3–5 и 7: Load — только Full, новый UUID, префикс `<PREFIX>`, типовое — только через расширение.
   Набор comol не установлен (навыку нужны его правила) — новый объект создает пользователь в Конфигураторе по описанию
   агента: что, где, свойства, типы. Вернуть прежний запрет может пользователь; решение записать в паспорт (п. 0) с датой.
3. **Загрузка конфигурации/расширения — только Full.** Partial / `-listFile` / точечная загрузка формы запрещены всегда
   (частичная загрузка расширения дает неполную подгрузку). `UpdateDB` — отдельной командой после Load, без лимита
   времени, никогда в одной команде с Load. Между Load и UpdateDB — CheckModules (п. 3 гейтов).
4. **GUID.** Новый объект или копия → новый уникальный UUID (`[guid]::NewGuid()` / `uuid.uuid4()`). Никогда не
   копировать UUID с образца, никогда псевдо-последовательные (`a1b2c3d4-…`). Перед каждым Load — проверка UUID
   (`scripts/1c/uuid-check.py`, ее вызывает `designer.ps1`).
5. **Префиксы.** Новые объекты расширения и новые процедуры/перехватчики в заимствованных модулях — с `<PREFIX>`.
   Реквизиты на наших (`<PREFIX>*`) объектах — без повторного префикса. Внешние обработки — файл `<PROJECT>_<Имя>_vX_Y_Z.epf`.
   Имена: аббревиатуры отделять `_` (`пр_АРМ_ОТК`, а не `пр_АРМОТК`) — иначе синоним нечитаем; синоним — имя
   словами + суффикс проекта, если он принят.
6. **Без буквы «ё/Ё»** в любых сырцах 1С (код, метаданные, строки, XML). В документации и переписке — можно.
7. **Типовая конфигурация напрямую не меняется** — только через расширение. Приоритет: подписка на событие >
   перехватчик в расширении (`&Перед`, `&После`, `&Вместо`, `&ИзменениеИКонтроль`) > правка типового (только после
   явного подтверждения пользователя).
8. **Docker: только `stop`, никогда `rm` / `compose down`** без явной просьбы пользователя. Общие контейнеры (граф,
   1c-*-mcp, v8std) не пересоздавать и не останавливать — ими пользуются другие проекты. Свой — только индексатор кода проекта.
9. **Область = запрос пользователя.** Не расширять на соседние проекты, базы, контейнеры, файлы. Неясная область — один
   уточняющий вопрос, а не максимальный охват.
10. **Не фантазировать выполненную работу.** После Dump/Load/UpdateDB/теста — проверить фактом (лог Конфигуратора, MCP,
    запрос через MCP 1С, отчет Vanessa) или попросить пользователя подтвердить в интерфейсе. Не писать «загружено», «работает»,
    «тесты зеленые» без доказательства.
11. **Хранилище конфигурации.** Если конфигурация/расширение на хранилище 1С — агент базу не трогает (никаких
    LoadConfigFromFiles/UpdateDBCfg/захвата): показывает готовый код и путь объекта, пользователь вносит сам.
12. **«Выгрузить свежий» = Dump из живой базы сейчас**, не архив с диска и не откат версии.
13. **Чистое дерево / чистить за собой.** Временные артефакты (пробы, дампы, логи, выгрузки, JSON, скриншоты)
    — только в `F:\AI_1C\harness\temp\` или в `temp/` папки проекта (`F:\AI_1C\projects\<PROJECT>\temp\`), не в корень
    харнеса, не в сырцы, не в `upstream`. По завершении задачи — удалить содержимое temp. Не оставлять
    `_dump_report.txt`, `*.log` в сырцах, пустые `src_temp/`, `Srvr=*`. В git не попадают `temp/*` (кроме keep),
    `indexes/`, `.env*`, секреты, бинарники.
14. **Версионирование — каждое изменение поставки = новая версия.** Правка XML `ext`, обработки, слияние с боевой →
    bump SemVer и новый бинарник, без исключений. Синхронно: `<Version>` в `Configuration.xml`, файл `VERSION`, имя
    бинарника `<PROJECT>_<ИмяЛатиницей>_vX_Y_Z.cfe`, прошлый бинарник → `old/`. Три независимых трека, не путать:
    настройки агента (`F:\AI_1C\harness\VERSION`, после bump — строка в `docs/changelog.md` харнеса: правка действует на все проекты), сырцы расширения
    (`SRC_ROOT\VERSION`), каждая внешняя обработка (`build/<Имя>/VERSION`, первая публикация строго `1.0.1`).
    Patch — мелкая правка; minor — новые реквизиты/механизм/скрипт; major — смена концепции/пайплайна.
15. **Поставка расширения закрывается свежим `.cfe`** (выгрузка `DumpCfg` из базы после UpdateDB), а не словами «сырцы
    обновлены». CFE не собирается «руками» из XML или чужими упаковщиками — только через Конфигуратор (Full Load →
    UpdateDB → DumpCfg). Исключение — пользователь прямо сказал принять файл боевой как есть.
16. **Обязательные проверки перед «готово» — не факультатив** (п. 3). Пропуск гейта = работа не сделана.
17. **Секреты.** Пароли, токены, лицензионные ключи — никогда в git, в чат, в логи, в отчеты. В выводе команд и MCP
    маскировать `/P"…"` и значения паролей. Пароль пользователя базы — только в `config/project.env.local`.
18. **Общие ресурсы машины** (см. п. 6): на одном порту MCP Vanessa живет один комплект TM+TC; свои процессы
    останавливать только по своему шаблону (своя база и свои порты в командной строке), чужие 1С-процессы не трогать. Перед
    настройкой общего ресурса — проверить, не занят ли он соседней сессией/агентом.
19. **Чужой контур не менять.** Чат не переименовывать без просьбы. Каталоги других проектов и других агентов только
    читать. Свои пути — в паспорте (п. 0), не в этом файле.

## 2. Общение с пользователем

- Ответы, вопросы, `brief`/`tz`/`log` — по-русски. Код, имена метаданных, пути, команды, имена MCP-инструментов — как есть.
- Пользователь пишет «МСП» — это MCP. Называет сервис или живую базу числом порта — имеется в виду сервис этого
  проекта из паспорта (живая база — MCP 1С), не переспрашивать.
- Долгая операция — статус в чат не реже раза в 5 минут: что готово, что идет, следующий шаг. Не уходить в тихое ожидание.
- Файлы, которые пользователь может открыть, — только markdown-ссылкой `[имя](путь)` (путь относительно рабочей папки,
  прямые слэши, пробелы — `%20`). Путь только в backticks или в `<…>` не кликается.
- Инструкции переноса в Конфигуратор — целиком в ответе: что создать/поменять, свойства, шаги. **Код — целыми
  процедурами**: измененная процедура — полный текст («заменить процедуру целиком»), небольшой модуль — полный текст,
  большой — «заменить весь текст» + ссылка на файл. Не давать «вставить между X и Y».
- Списки объектов метаданных — по алфавиту (без учета регистра, как в дереве Конфигуратора), сгруппированные по виду.
- Перед сдачей результата — разбор соответствия: каждое требование пользователя (и материалы: ТЗ, видео, замечания) —
  «выполнено / частично / нет» с доказательством. Не выполнено — вернуться к коду и тестам, а не сдавать.
- **Перед ответом пользователю** — обязательный проход `rules/verify-before-reply.md`: перечитать запрос, сверить с
  арtefact (лог, json, cfe, ping MCP), при FAIL/blocker дожать самому где можно; Vanessa/PMI — pass/fail только из
  файлов отчетов; не писать «готово», пока DoD пользователя не закрыт.
- **Vanessa-тесты** — цикл написания, прогона, сверки через MCP 1С и границ правок кода: `rules/vanessa-testing-methodology.md`
  (полный/частичный цикл, протоколы, блоки ЕСКС/ЕСУЗ/ЭОЖ/МК).
- Не открывать пользователю файлы и папки (Проводник, Блокнот, `Start-Process`) — только ссылки.
- Управление экраном пользователя (computer-use, клики мышью по его рабочему столу) — не использовать.

## 3. Гейты проверки (по порядку, обязательно)

| Что правил | Обязательно |
|------------|-------------|
| любой `.bsl` | `1c-syntax-checker-mcp` (`syntaxcheck`, файл — `scripts/mcp/syntaxcheck_file.py`) на каждый измененный модуль |
| тексты запросов в модулях | компиляция на живой базе: `scripts/1c/check-query-texts.py <модули>` (через MCP 1С) |
| новый «общий» код (файлы, длительные операции, строки, пользователи, печать) | конфигурация на БСП — сначала `1c-ssl-mcp` `ssl_search` (есть ли готовое в БСП, с поправкой на версию БСП базы); без БСП — механизмы самой конфигурации через индексатор |
| `Form.xml` | `1c-forms-mcp` `validate_form` (файл — `scripts/mcp/validate_form_file.py`) + skill `form-validate`; каждое `Элементы.<Имя>` модуля есть в форме |
| вопрос о стандарте или номере диагностики | `v8std` (`v8std_search`, `v8std_explain_diagnostics`), не по памяти |
| новые или измененные объекты метаданных | навык `1c-metadata-manage`, затем skills `meta-validate` / `cfe-validate`, проверка UUID |
| после Full Load, до UpdateDB | `scripts/1c/check-modules.ps1` — CheckModules `-ThinClient -WebClient -Server -MobileClient` |
| после UpdateDB | `scripts/1c/dump-cfe.ps1` → свежий CFE; тест Vanessa по затронутому блоку |

Порядок мысли перед «готово»: синтаксис → логика и производительность → стандарты (п. 4) → анализ влияния (кто еще
ссылается: `find_references`, `get_callers`, граф `find_usages_of_object`) → валидация XML. В конце — короткая сводка:
что изменено, файлы, источники контекста, риски, хвосты.

## 4. Стандарты кода BSL (кратко; подробно — `docs/07_Грабли_платформы_и_тестов.md`, v8std)

- Табуляция, методы ≤ 200 строк, строки ≤ 120, без длинного тире «—» в коде и строках 1С, без `?()`, без голого `Сообщить()` для пользовательского потока, без
  «йода»-сравнений, без венгерской нотации; русские имена.
- Модули — стандартные области std455 (`ПрограммныйИнтерфейс`, `СлужебныйПрограммныйИнтерфейс`,
  `СлужебныеПроцедурыИФункции`, в формах `ОбработчикиСобытийФормы`, `ОбработчикиКомандФормы` и т.д.); большие области —
  подобласти по темам; пустых областей нет.
- У каждого метода — описание std453 над директивой компиляции: глагол («Возвращает…», «Проверяет…»), `Параметры:`,
  `Возвращаемое значение:`. Обработчики — одной-двумя строками по смыслу, не «Обработчик события ПриОткрытии».
- Запросы — параметризованы, с псевдонимами, никогда в цикле; `ПЕРВЫЕ N` где нужно; без обращения «через точку» в
  горячих местах; без подзапросов в `ВЫБРАТЬ`.
- Транзакции: `НачатьТранзакцию / Попытка / ЗафиксироватьТранзакцию / Исключение / ОтменитьТранзакцию / ВызватьИсключение`;
  управляемые блокировки; длительные операции — через подсистему БСП «Длительные операции» (если БСП есть); время — серверное.
- Повторяющиеся конструкции — в маленькие общие помощники; мертвые обработчики — удалять вместе с привязкой в `Form.xml`.
- В модуле формы не называть локальные переменные именами свойств формы (`Окно`, `Заголовок`, `Элементы`) — присваивание
  падает, а внутри `Попытки` ошибка не видна.

## 5. MCP (подробно — `docs/02_MCP.md`)

| MCP | Адрес | Для чего | Когда обязателен |
|-----|-------|----------|------------------|
| индексатор кода (`<PROJECT>-code-index`, свой контейнер) | `:<CODE_INDEX_PORT>` | поиск кода и метаданных conf/ext, вызовы, ссылки, структура объектов, права ролей | любое чтение метаданных/кода базы |
| `graph-mcp` (общий) | `:8006` | граф метаданных: связи объектов, кто пишет в регистр, влияние изменения, формы, права; `project_id` обязателен | анализ влияния, связи, «кто использует» |
| `1c-syntax-checker-mcp` | `:8002` | BSL LS: синтаксис и стиль | каждая правка `.bsl` |
| `1c-docs-mcp` | `:8003` | справка платформы, стандарты | синтаксис встроенного языка, методы платформы |
| `1c-templates-mcp` | `:8004` | библиотека шаблонов кода + память проекта | типовые приемы, запомнить решение |
| `1c-ssl-mcp` | `:8008` | поиск по API БСП (последних версий — сверять с версией БСП базы) | перед написанием общего кода, если конфигурация на БСП |
| `1c-forms-mcp` | `:8011` | генерация и валидация `Form.xml` | каждая правка формы |
| `v8std` | `:18766` | стандарты v8std.ru, объяснение диагностик | вопрос о стандарте/диагностике |
| MCP 1С (`<PROJECT>-1c`, HTTP-сервис в базе) | `:<MCP1C_PORT>/<MCP1C_APP>/hs/mcp`, Basic | `execute_code`, `execute_query`, метаданные живой базы | подготовка/вайп/проверка данных тестов, компиляция запросов, журнал регистрации |
| Vanessa MCP (в TestManager) | `:<VANESSA_MCP_PORT>` | управление тестированием UI: клиенты, сценарии, шаги, формы, скриншоты | тесты интерфейса |

- `v8std` — только локальный `:18766`; публичный `https://ai.v8std.ru/mcp` для кода проекта не использовать.
- Коннектор MCP в сессии не поднялся, а сервер жив (`/health`, `docker ps`) — вызывать по HTTP:
  `python scripts/mcp/mcp_http.py <порт> <инструмент> '<json>'` (`--list` — список инструментов).
- Индексатор не видит изменений файлов с диска Windows: после выгрузки, загрузки боевой, крупных правок —
  `scripts/mcp/code-index/reindex.ps1` (инкрементально по хешам). Признак устаревшего индекса — `grep_code` не находит
  текст, который точно есть в файле. Граф после правки — `refresh_graph_project` / `refresh_extension_layers`.
- **MCP 1С** (`docs/03_MCP_1С.md`): расширения `MCP_Сервер` (коробка, не менять) и `MCP_ВыполнениеКода` ставятся только
  `scripts/mcp1c/install-mcp.ps1` (без безопасного режима, с согласия пользователя), публикация — только 127.0.0.1 с
  Basic-авторизацией. UpdateDB — через `designer.ps1` (сам останавливает пул IIS и сеансы публикации). Чтение данных
  сразу после действия в интерфейсе — запросами (кэш сеанса ~20 с).

## 6. Тестирование (подробно — `docs/04_Vanessa.md`, `docs/03_MCP_1С.md`)

- **Два слоя.** Данные готовятся, вычищаются и проверяются через MCP 1С (`execute_code` из BSL-файлов, только HTTP из
  скриптов). Документы в тестах создаются и проводятся **только через интерфейс** (Vanessa), не через `execute_code`.
- **Микрокомандное управление.** Раннер шагов (`scripts/vanessa/run_steps.py`) ведет прогон по списку шагов: вайп и
  подготовка (MCP 1С) → подключение нужного клиента → одна фича = один вызов `run_scenario` → результаты по шагам
  (`get_test_results`) → проверка данных (MCP 1С) → следующий шаг. После каждой фичи — короткий отчет в чат.
- **Классический плеер фич (StartFeaturePlayer) запрещен** — только MCP-режим Vanessa по HTTP.
- **Лог побеждает вердикт MCP.** После каждого шага смотреть результаты по шагам и лог, даже при `Success`. Ответа нет
  дольше 60 с — промежуточный статус в чат; таймаут — FAIL.
- **Проверять реальное состояние** (статусы, количество строк, движения, диалоги), а не «ошибки не было». Неверное
  состояние при «Success» — дефект продукта, а не повод ослабить тест.
- **Без искусственных пауз** (`И Пауза N`) — ждать готовности («в течение N секунд»).
- **Вайп тестовых данных перед каждым полным прогоном.** Полный прогон набора — после правки кода продукта; если упала
  сама фича (порядок шагов, устаревшее ожидание), а код не менялся, — исправить фичу и прогнать только ее.
- **Свежие сеансы.** TM/TC перезапускаются (`scripts/vanessa/restart-vanessa.ps1`) только после обновления базы/CFE,
  после правки VAParams или когда порт MCP не отвечает; на обычный FAIL шага — не убивать (следующая фича сама закрывает
  окна). Профиль «Этот клиент» — без пароля: подключаться только к уже поднятому скриптом клиенту, иначе Vanessa
  стартует клиент сама, вход не проходит, и после нескольких попыток платформа блокирует пользователя.
- **Отчет о прогоне** — таблица ✓/✗/! по фичам и шагам; у каждого ✗ — цитата из лога, у каждого ! — причина.
- **После любой правки расширения** агент сам, без напоминания: bump → Full Load → CheckModules → UpdateDB → CFE →
  прогон фич затронутого блока → новая/обновленная фича под изменение → полный прогон блока до fail=0. Пропуск — только
  по явному «пропусти тестирование».
- **Долгие прогоны** — штатным фоном инструмента агента (видимым и останавливаемым), не `&`/`Start-Process` в обход.
  Остановка прогона = убить раннер **и** пару TM/TC (отправленный сценарий доигрывается в Vanessa без раннера).

## 7. Сессии, задачи, параллельная работа

- Новый чат — новая папка `tasks/YYYY-MM-DD-кратко/` из `tasks/_template`, сразу, не в конце. Продолжение — та же
  папка: прочитать `brief.md` и хвост `log.md` до правок. Пользователь не назвал задачу — спросить: новая или
  продолжить (показать список `tasks/`).
- В `log.md` этой папки писать каждый запрос пользователя дословно и ответ, который ушел в чат. Секреты (пароли,
  токены, ключи) в папку не писать: вместо значения — «секрет, в лог не записан». После сжатия контекста или в новом
  чате это единственный источник правды, не память агента.
- `brief.md` — постановка и приемка, `tz.md` — план и чек-лист, `log.md` — запросы, ответы, решения, что дальше.
- Сложная задача (несколько объектов, крупная форма, новый механизм) → сначала план и `tz.md` с чек-листом приемки,
  потом маленькие проверяемые батчи, потом проверка. Мелкий фикс — без этого.
- Параллельные сессии/агенты разрешены. Перед работой с общим (база, пул и сайт IIS MCP 1С, Vanessa, Docker, `AGENTS.md`, `log.md`)
  — проверить, не занят ли он (процессы 1С по командной строке, свежие отчеты, время изменения файла); занят —
  договориться о порядке, не писать поверх чужих правок.

## 8. Git (только локально)

- Репозитории без remote, push не делать никогда. Три репозитория, не один: харнес `F:\AI_1C\harness` (правила, skills, скрипты, каталог MCP — правка здесь видна всем проектам), папка проекта `F:\AI_1C\projects\<PROJECT>`, сырцы `F:\AI_1C\projects\<PROJECT>_src` (в git только `ext/` и исходники обработок `build/*/src`; `conf/`, индексы — вне git). `core.autocrlf=false` — сырцы 1С байт в байт.
- Автор — в самой команде: `git -c user.name=<имя> -c user.email=<имя>@<проект>.local commit …` (глобальный конфиг не менять).
- **Каждый bump версии — коммит + аннотированный тег `vX.Y.Z` в своем репозитории**, агент делает это сам по
  завершении версии. Бинарники (`.cfe/.cf/.epf`) — в git не класть: файлами в `build/`, прошлые — `build/old/`.
- Никогда в git: `config/project.env.local`, `.env*`, секреты, `indexes/`, отчеты Vanessa, pid-файлы.

## 9. Поставка

- Итог — готовый файл (`.cfe`/`.epf`/`.docx`…): markdown-ссылка на него + полный путь; если клиент агента умеет
  отправлять файлы пользователю — дополнительно отправить. Сырцы XML, логи, `.env`, ключи — не отправлять.
- Выпуск в боевую, которую ведут и другие разработчики: 1) свежая копия боевой → снимок и трехстороннее сравнение
  (прошлая боевая — наша — свежая боевая); 2) агент сам доводит нашу версию до боевой (изменения только боевой — как
  есть, «двойные» объединяет, чинит обращения к переименованному/удаленному боевой), полный прогон, CFE и **дельта к
  свежей боевой** (что захватить, свойства, процедуры целиком, тексты запросов); пользователь переносит ровно дельту —
  CFE целиком в боевую не загружается; 3) пользователь выгружает результат — агент сверяет с нашей CFE и со снимком
  (дельта перенесена, ничего не пропало и не сломалось), только тогда боевая — основная. Скрипты-образцы — `examples/energy/scripts/git/` (`changes_since_prod.py`, `three_way_prod.py`,
  `verify_prod_cfe.py`), порядок — `docs/05_Цикл_доработки_расширения.md`.
