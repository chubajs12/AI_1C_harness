# Полный цикл 1С в Harness

Источник — правила проекта (`.claude/rules-1c/subagent-pipeline.md`, `verification-gates.md`,
`verification-policy.md`, `subagents.md`), которые пришли из набора comol/ai_rules_1c. Ниже — рабочая
последовательность для Harness, без пересказа всех правил.

## 1. Триаж (родитель, до любых правок)

Прочитать `.claude/rules-1c/verification-policy.md` и выбрать путь:

| Путь | Признак | Что делать |
|---|---|---|
| docs-fix | только текст, нет проверяемых 1С-фактов | структурные проверки файлов, BSL-валидаторы не нужны |
| spec-authoring | OpenSpec с конкретными 1С-фактами | сначала подтвердить факты через MCP, потом писать спеку |
| quick-fix | одно изменение в одном модуле ≤ `QUICKFIX_MAX_LINES` (40) или изолированное несвязанное добавление метаданных | план в две строки → правка → гейты на `VERIFICATION_DEPTH` |
| full-cycle | всё остальное, любая транзакция/публичный контракт/связанные метаданные/RLS/подписка/задание | шаги 2–5 |

Сомнение → full-cycle.

## 2. План

- Роль: `planner` (или `architect`/`analytic`/`explorer` по форме задачи) — см. навык `1c-delegation`.
- План: нумерованные задачи, у каждой — точные файлы и точные имена процедур; точки проверки на модуль, а не на
  каждые 20 строк; DoD с привязкой к проверкам; риски и откат.
- **Утверждение пользователем обязательно**, если план трогает: транзакции/проведение, публичные контракты, связанные
  метаданные, заимствованные объекты, RLS/роли, подписки, регламентные задания, или необратим. Иначе — опубликовать
  план в чате и продолжить, одной строкой отметив это.
- Идущая OpenSpec-правка (`openspec/changes/<change>/proposal.md` + `design.md` + `tasks.md`) — это и есть
  утверждённый план: заново не планировать.

## 3. Реализация

- Роль: `developer` / `metadata-manager` / `refactoring` / `performance-optimizer` / `error-fixer`.
- Метаданные — только навыком `.claude/skills/1c-metadata-manage/SKILL.md` или ролью `metadata-manager`; правка XML
  руками — только в исключениях навыка, с проверкой контекста до и XML после.
- Валидаторы по каждому затронутому модулю: `syntaxcheck` (по пути файла) → `check_1c_code` → `review_1c_code`;
  для XML — `verify_xml`. Бюджет: один чистый прогон на актуальное состояние, правка при блокирующем дефекте —
  и один подтверждающий прогон. Прогон по неизменённому содержимому запрещён.

## 4. Ревью

- 4a соответствие плану (родитель): все задачи выполнены, вне плана ничего не тронуто (`git diff --name-only`),
  сигнатуры новых процедур совпадают, UUID не перегенерированы, шапки процедур на месте.
- 4b качество кода (родитель): антипаттерны, платформенные решения, ITS-стандарты, предупреждения BSL LS, запросы,
  транзакции, блокировки, границы проведения. `code-reviewer` — только по явному запросу.
- Находки: critical / major / minor; critical и major закрываются до сдачи, minor — информационно.

## 5. Верификация и сдача

- Закрыть `verification-gates.md`, переиспользуя свежие доказательства стадии 3; недостающие гейты — прогнать.
- Поведенческое подтверждение: UI — только Vanessa в RDP (`UI_TESTING`), свои сеансы 1С после тестов закрывать.
- Сверка с DoD по текущим доказательствам, а не по отчёту субагента.
- В ответе: что изменено, каждый файл, чем проверено, что осталось непроверенным и почему. Строки доказательств —
  только применимые: `Memory:`, `Template:`, `Docs:`, `Metadata tooling:`, `IB tooling:`, `Repository tooling:`.
- Выпуск в боевую при общей разработке — трёхсторонняя сверка (`~\.dsh\AGENTS.md`, раздел «Выпуск в боевую»).

## Запрещено

- Объявлять «загружено/сделано» без подтверждения (MCP-ответ, UI пользователя, вывод валидатора).
- Расширять область: соседние проекты, контейнеры, «заодно» починить.
- Load конфигурации/расширения частично — только Full, UpdateDB отдельной командой.
- Запускать OneBridge, `/installmcp`, `/setupmcp`, `/updatemcp`.
