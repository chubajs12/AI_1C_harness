# Перед ответом пользователю (verify-before-reply)

Обязательный финальный проход **каждого** сообщения пользователю, если в ходе хода была работа по задаче (не короткий FAQ без арtefactов).

## Порядок

1. **Перечитать исходный запрос** — последнее сообщение пользователя и явный DoD (ТЗ, чек-лист, «принято когда…»). Не подменять формулировку своим кратким пересказом при сверке.
2. **Сверить с арtefact** — факты только из проверяемых следов: лог Конфигуратора / скрипта, JSON отчета, свежий `.cfe`/`.epf`, вывод `mcp_http.py` / `/health`, файл прогона Vanessa, PMI-отчет, `tasks/*/log.md`. Нет арtefactа — нет утверждения «сделано» / «pass».
3. **FAIL / blocker / неполный результат** — если агент может дожать в рамках задачи (повторный прогон, правка, перезапуск TM/TC, RDP/интерактив по запросу пользователя) — **сделать**, затем снова п. 2. Сдавать «BLOCKER» финалом только после **осмысленной** попытки и явного перечня того, что недоступно без человека или вне области.
4. **Vanessa и PMI** — вердикт pass/fail только из **файлов отчетов** (лог шагов, `get_test_results`, итоговый отчет раннера). Успех MCP-вызова без разбора лога шагов не считается зеленым прогоном (`AGENTS.md` п. 6).
5. **«Готово»** — только когда DoD пользователя закрыт по п. 2–4 или явно зафиксировано «частично / нет» с доказательством и остатком работ (`AGENTS.md` п. 2, `verification-delivery.md`).

## Антипаттерны

- Финальный ответ с BLOCKER без повторного прогона или fix, который агент мог выполнить сам.
- «Тесты зеленые» / «Vanessa OK» по памяти или по `Success` без цитаты из отчета.
- «Готово» при открытых пунктах DoD или без таблицы «выполнено / частично / нет».
