# Как ставились правила (история харнеса Energy)

Почти каждое правило в `AGENTS.md` появилось после конкретного случая: ошибка агента, замечание пользователя, сбой
инструмента. Принцип: случилось → разобрали причину → правило записано на диск (правила проекта + строка в changelog с
bump версии настроек) → следующий раз проверяется по правилу, а не по памяти. Полный журнал — `reference/energy/
changelog.md` (версии харнеса от 0.9), полный свод правил Energy — `reference/energy/CLAUDE.md`.

## Этап 1. Cursor (август — сентябрь 2026)

Проект начинался в Cursor: ~30 правил `.mdc` + ~80 skills. Выводы, перенесенные дальше (`reference/energy/lessons.md`):

| Проблема | Вывод |
|----------|-------|
| XML конфигурации 2–4 ГБ съедает контекст | только MCP и точечные файлы |
| модели фантазируют про платформу | справка и синтаксис через MCP, запрет выдумок |
| длинный свод правил теряется после сжатия контекста | короткие обязательные правила + skills по запросу + состояние задачи на диске |
| «выгрузил» без факта | не считать сделанным без подтверждения |

Правила Cursor того периода (сохранены в changelog): единые карты через один механизм (`maps-nextgis-canon`), защита
чужих форм НСИ от затирания при загрузке, вайп обязан сносить ссылки на дефекты до удаления дефектов, роли — категории
Чтение / Редактирование / СозданиеРедактирование (чистое «Создание» платформа не допускает), сборка только
Конфигуратором (`no-build-without-designer`).

## Этап 2. Перенос в Claude Code (20 сентября 2026)

- ~30 правил `.mdc` собраны в один `CLAUDE.md` (общий для всех проектов — глобальный, специфика — проектный).
  Причина: у Claude нет переключателя «правило по запросу», весь файл читается каждый ход — значит, обязательное
  должно быть сформулировано как обязательное.
- **Аудит Cursor:** `v8std` — 0 вызовов, синтаксис — ~3% ходов с правкой BSL, потому что правила были «по желанию».
  → Гейты проверки стали жестким правилом (п. 17 Energy, `AGENTS.md` п. 3).
- Перенесены 50 skills из ~80: только те, что не противоречат «агент не создает метаданные» (без `meta-compile`,
  `cf-edit`, `role-compile` и т.п.). Правило снято 20.10.2026 (таблица ниже): создание объектов — навык comol
  `1c-metadata-manage`.
- **Пробел переноса:** методика «Vanessa MCP micro» из трех правил Cursor потерялась — осталась ссылка без содержания.
  Найдено и восстановлено в тот же день (молчать >60 с нельзя, лог побеждает вердикт, не убивать TM/TC на FAIL,
  перечитывать фичу).
- **Параллельные сессии:** два одновременных `docker compose up` под одним именем проекта пересоздавали контейнеры
  друг друга, две сессии чуть не правили один `CLAUDE.md`. → Правило не «запретить параллельность», а «проверять общий
  ресурс перед работой с ним» (раздел про параллельные сессии).

## Этап 3. Инфраструктура (20 — 29 сентября)

- **TLS-прокси для MCP** (20–28.09): казалось, что приложение требует `https://` для коннекторов; поднимали caddy, нашли
  в нем баг выдачи сертификатов. Оказалось, обычный `http://localhost` работает. → Прокси удален; правило: при
  подозрении на регрессию сначала перепроверить поведение, не поднимать по старой памяти.
- **Два комплекта Vanessa на одном порту** (21.09): скрипты рестарта ext и МП убивали только «свои» процессы и не
  видели чужие; на `:9874` оказались два TM. → Один комплект на порт; перед стартом искать и гасить пары обоих
  контуров по командной строке.
- **Опечатка в VAParams** (`КаталогВыгрузкиЛогОшибок`) полтора дня вешала очередь МП модалкой. → Ключ проверять первым.
- **`stop_scenario` перед каждой фичей** сам вызывал модалку VA. → Прогон одной фичи напрямую, без упреждающего stop.
- **Номер RDP-сессии сменился** (9 → 3), фильтр по номеру молча ничего не находил. → Искать по имени/командной строке.
- **Локальный git** (23.09): пользователь увидел похожий на GitHub адрес автора и уточнил «только локально». → Без
  remote, автор через `-c`, коммит + тег на каждую версию — агент делает сам. История версий восстановлена из
  сохраненных CFE (временная база → XML → коммит с датой файла).
- **Ответы только по-русски**, «МСП» = MCP, живая база по приблизительному номеру порта — из замечаний пользователя.
- **MCP 1С вместо OneBridge** (16.10.2026): OneBridge — толстый клиент с обработкой — падал при нехватке памяти хоста,
  висел с закрытым портом, держал сеанс и мешал UpdateDB, его окна и диалоги оказывались на консоли пользователя.
  Замена — HTTP-сервис расширения на IIS: коробку `MCP_Сервер` не меняем, свои инструменты — отдельным расширением;
  расширения — без безопасного режима через служебную обработку (Конфигуратор ставит в безопасном); свой пул IIS, чтобы
  остановка перед UpdateDB не задевала соседей; публикация только на 127.0.0.1.
- **Общий граф на все проекты** (29.09, решение пользователя): отдельные графы проектов удалены; один `graph_mcp` с
  `project_id`; одна очередь индексации. **Индексатор** пересобран на 1.8.5 обычным `docker run`; его данные сначала
  положены соседней папкой `energy_mcp` — пользователь: «почему отдельная папка, а не внутри energy?» → данные MCP
  проекта — только внутри папки проекта (`indexes\`).
- Полная переиндексация ERP — 5 часов; пользователь пояснил, что на старом контуре было 2–3 дня. → Часы — норма, не
  повод считать, что «зависло».

## Как добавлять правило дальше

1. Случай → причина (не симптом) → формулировка «что делать», а не «что случилось».
2. Записать в `AGENTS.md` в раздел по теме (или в `docs/0X_*.md`, если это процедура), с одной строкой «почему».
3. Bump версии настроек (`VERSION`), строка в `docs/changelog.md`, коммит + тег.
4. Если правило — проверяемое, сделать его скриптом/гейтом (как `check-modules.ps1`, `check-query-texts.py`,
   автосортировка): скрипт нельзя «забыть», правило в тексте — можно.
