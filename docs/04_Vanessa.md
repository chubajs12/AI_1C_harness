# Vanessa Automation: как устроено тестирование и микрокомандное управление

## 1. Архитектура

```
Сеанс пользователя (console)                         RDP-сессия Windows-пользователя «vanessa»
┌──────────────────────────────┐                     ┌─────────────────────────────────────────────┐
│ агент (Claude Code / другой) │  HTTP :VANESSA_MCP  │ TestManager: 1cv8c /TESTMANAGER             │
│   run_steps.py / run_feature │ ──────────────────► │   vanessa-automation-single.epf (VA)        │
│   vac.py (одна микрокоманда) │                     │   расширение client_mcp → MCP-сервер :9880  │
│                              │                     │        │ управляет по порту TestClient      │
│ MCP 1С (IIS → сервер 1С)     │  HTTP :MCP1C        │        ▼                                    │
│   вайп / подготовка / проверки ◄──── агент        │ TestClient: 1cv8c /TestClient -TPort 1539   │
└──────────────────────────────┘                     │   окна приложения, по которым кликает VA     │
              │                                      └─────────────────────────────────────────────┘
              └──────────── одна и та же база (сервер/база) ─────────────┘
```

- **TestManager (TM)** — тонкий клиент с ключом `/TESTMANAGER`, в нем открыта обработка Vanessa Automation (single,
  1.2.043.28). Исходники и релизы — [Pr-Mex/vanessa-automation](https://github.com/Pr-Mex/vanessa-automation)
  (файл `vanessa-automation-single.1.2.043.28.zip`; на GitHub есть новее, в комплекте закреплена 1.2.043.28).
  Расширение **`client_mcp`** (0.6.5, компонента WebTransportAddIn — есть сборки Windows и Linux)
  поднимает в TM HTTP MCP-сервер на `VANESSA_MCP_PORT`: агент управляет Vanessa инструментами (`run_scenario`,
  `connect_test_client`, `get_test_results`, `get_form_analysis`, `get_window_screenshot_os` и еще ~30).
- **TestClient (TC)** — второй тонкий клиент той же базы с `/TestClient -TPort <порт>`: в нем Vanessa открывает формы,
  нажимает кнопки, вводит значения. Расширение **`VAExtension`** (1.29) в базе дает дополнительные шаги (например,
  «И я выполняю выражение '…' в текущем окне (Расширение)»).
- **Отдельная RDP-сессия.** Окна TM/TC живут в сессии отдельного Windows-пользователя (`vanessa`): они не мешают
  рабочему столу пользователя, а Vanessa не мешает пользователь. Сессию можно отключить (Disconnected) — она живет.
  Агент запускает пару в ней без пароля: задача планировщика от SYSTEM → `wts-launch.ps1` (WTSQueryUserToken +
  CreateProcessAsUser) → `start-tm-tc.ps1` в сессии `vanessa`.
- **MCP 1С** (HTTP-сервис расширения в базе, `03_MCP_1С.md`) — второй канал в ту же базу: данные готовятся,
  вычищаются и проверяются им, а интерфейс — Vanessa. Это и есть «два слоя» тестирования.

Файлы комплекта: `tools/vanessa/` — `vanessa-automation-single.1.2.043.28.zip` (распаковать в `tools/vanessa/single/`),
`client_mcp.cfe`, `VAExtension.1.29.cfe`, `ASSERT-PATTERNS.md` (шаблоны проверок в фичах из Energy).

## 2. Разовая настройка (первый запуск, `08_Первый_запуск.md`)

1. Служебные расширения в базу проекта — `scripts\1c\load-helper-extensions.ps1` (с согласия пользователя: меняет базу).
   После — у расширений снять «Безопасный режим» и «Защиту от опасных действий» (Конфигуратор → Конфигурация →
   Расширения конфигурации, или в режиме предприятия «Все функции → Управление расширениями»); проверка —
   `python scripts\mcp1c\mcp1c.py tests\smoke\bsl\env_check.bsl` (`безопасныйРежим: false`, `активно: true`).
   У пользователя базы, под которым идут тесты, — снять «Предупреждать об опасных действиях» (иначе диалоги на EPF).
2. Windows-пользователь и RDP-сессия — `scripts\vanessa\setup-vanessa-user.ps1` (если на машине уже есть общий
   `vanessa` — только `-OnlyAcl`: права на каталоги проекта) и `scripts\vanessa\connect-rdp.ps1` (войти один раз).
3. Задача планировщика запуска пары — `scripts\vanessa\register-launch-task.ps1` (администратор, один раз).
4. VAParams — `python scripts\vanessa\make_vaparams.py` (каталог фич, отчеты, профиль «Этот клиент»).
5. Пара — `scripts\vanessa\restart-vanessa.ps1`; затем дымовой тест
   `python scripts\vanessa\run_steps.py tests\smoke\steps.json` (фичу под вашу конфигурацию пишет `make_smoke.py`).

Порты своего проекта (`VANESSA_MCP_PORT`, `VANESSA_TC_PORT`) — не те, что у Energy (9874/1538): на одном порту MCP
может жить только одна пара (в Energy два комплекта на одном порту путали окна — «ссылка получена для другого
приложения»). Все пути, которые получает Vanessa (фичи, отчеты, части фич, скриншоты), должны быть доступны
пользователю `vanessa` — не во временной папке агента (`%TEMP%` его профиля Vanessa не видит: «Файл … не существует»).

## 3. Микрокомандное управление тестированием

Идея: тест не «одна большая кнопка, которая гоняет все фичи вслепую», а цепочка маленьких команд, после каждой из
которых агент видит результат и решает, что дальше. Так ошибка ловится на первом шаге, где она возникла, с точным
местом и контекстом, а не через 40 минут в общей куче.

### Уровни

| Уровень | Инструмент | Что делает |
|---------|------------|-----------|
| одна команда MCP | `vac.py <инструмент> '<json>'` | любое действие Vanessa: подключить клиент, проанализировать форму, нажать кнопку, снять экран, прочитать результаты |
| одна фича | `run_feature.py <фича>` | connect (только к живому клиенту) → `run_scenario reloadAndRun` → `get_test_results` → вердикт по шагам |
| прогон блока | `run_steps.py <шаги.json>` | список шагов: подготовка через MCP 1С, рестарт/подключение клиента, фичи по одной, проверки данных |

### Шаги прогона (`run_steps.py`)

```json
[
  {"id": "P-01", "kind": "ob",      "target": "bsl/wipe.bsl"},
  {"id": "P-02", "kind": "ob",      "target": "bsl/nsi.bsl"},
  {"id": "R-01", "kind": "connect"},
  {"id": "F-10", "kind": "feature", "target": "features/10_create_order.feature", "timeout": 300},
  {"id": "K-10", "kind": "check",   "target": "bsl/check.bsl", "stage": "after_post"},
  {"id": "F-20", "kind": "feature", "target": "features/20_post_and_close.feature"}
]
```

- `ob` — BSL через MCP 1С `execute_code` (вайп, НСИ, фикстуры), PASS при `Результат.ok = Истина`.
- `check` — то же, `&ЭТАП` в тексте заменяется на `stage`: один файл проверок на разные этапы.
- `restart` — свежая пара (только после UpdateDB/CFE, правки VAParams, мертвого порта); `connect` — «Этот клиент».
- `feature` — одна фича; `connect: true` — подключить клиент перед ней (нужно первой фиче после рестарта).
- `python` — свой скрипт проверки (код 0 = PASS).
- Ключи: `--from ID` (продолжить с шага, данные предыдущих должны быть), `--only ID` (один шаг), `--until ID` (стенд
  для показа: подготовка до нужного состояния), `--dry-run`, `--continue-on-fail`, `--shots <каталог>`.
- Первый FAIL останавливает прогон: чинить по одному, не гонять дальше по сломанным данным.

Образец из Energy — `examples/energy/scripts/pmi/run_esks_arm.py` (≈50 шагов: вайп и НСИ через MCP 1С, тестовый
пользователь с ролями через профили БСП, цикл в тонком клиенте, переключение клиентов тестирования «Этот клиент» /
«АРМ клиент» (вход под тестовым пользователем), фичи АРМ, проверки данных после каждого блока, регламентное задание
через вызов обработчика, скриншоты для инструкций). В комплекте `run_steps.py` — та же схема, обобщенная на JSON.

### Как агент ведет прогон (дисциплина)

1. Перед полным прогоном — вайп тестовых данных (первые шаги файла). Тестовые данные несут префикс («ТЕСТ …») — вайп
   удаляет только их.
2. Долгий прогон — фоном инструмента агента (видимым и останавливаемым), не `&`. Вывод читать по ходу; `run_feature`
   печатает «идет N с» каждые 30 с. **Статус в чат после каждой фичи** и не реже раза в минуту на долгой фиче.
3. FAIL → открыть отчет фичи (`VANESSA_REPORTS/runs/<фича>.txt`: шаги со статусами, текст ошибки), при «непредвиденной
   ошибке» клиента — журнал регистрации через MCP 1С (`tests/templates/event_log_errors.bsl`, пользователь тестов): в отчете Vanessa текста
   ошибки платформы нет.
4. Решить, что сломано: **фича** (порядок шагов, имя элемента, устаревшее ожидание) → поправить фичу и прогнать только
   ее (`--only`, со своим вайпом/подготовкой, если нужно); **продукт** → правка кода, полный деплой, полный прогон.
5. Итог — таблица ✓/✗ по шагам (печатает раннер), у каждого ✗ — цитата из отчета.

### Ручная отладка микрокомандами

Когда фича падает непонятно — пройти руками через `vac.py`:

```powershell
python scripts\vanessa\vac.py get_window_list_testclient '{}'            # какие окна открыты
python scripts\vanessa\vac.py get_form_analysis '{"format":"elements"}'  # дерево элементов: ИМЕНА, видимость
python scripts\vanessa\vac.py get_form_analysis '{"format":"gherkin"}'   # состояние формы готовыми шагами
python scripts\vanessa\vac.py manage_form_elements '{"action":"click_button","element_name":"ФормаПровестиИЗакрыть"}'
python scripts\vanessa\vac.py get_form_analysis '{"format":"messages"}'  # сообщения пользователю
python scripts\vanessa\vac.py search_for_steps_by_keywords '{"search_name":"таблице|строк","limit":20}'
python scripts\vanessa\vac.py get_window_screenshot_os '{"window_title":"<окно>","color_mode":"color","file_name":"<путь, доступный vanessa>"}'
```

Найденные шаги/имена переносятся в фичу; фича прогоняется заново (`reloadAndRun` перечитывает файл с диска).
Справочник всех инструментов — `04a_Vanessa_MCP_инструменты.md`.

## 4. Как писать фичи

- Заголовок: `# language: ru`, `# encoding: utf-8`, теги; `Функционал:`; `Контекст:` — «И я закрываю все окна
  клиентского приложения», «И я активизирую TestClient "Этот клиент"».
- Одна фича — одна проверяемая операция (короткая, 1–3 минуты). ID сценария в имени (`Сценарий: F-10 ...`) — так
  результаты сопоставляются с ПМИ.
- **Имена элементов — из формы, не по видимым подписям**: `get_form_analysis` или `Form.xml` (индексатор
  `get_form_handlers`/граф `get_form_structure`). В БСП таблица списка пользователей — `ПользователиСписок`, а не
  `Список` — первая версия дымового теста комплекта упала ровно на этом.
- **Заголовки окон — шаблоном, если форма «умная»**: типовые формы сами решают, что открыть (ERP по ссылке на список
  валют открыл форму элемента «руб. (Валюта)», по пустому списку складов — «Склад (создание)»; список присоединенных
  файлов БСП выдает модальное окно «можно посмотреть только в форме объекта-владельца»). Проверять фактическое окно
  (`get_window_list_testclient`), а не ожидаемое по имени объекта.
- **Проверять состояние, а не отсутствие ошибки**: статусы, количество строк, значения полей, движения (через проверку
  MCP 1С после фичи). Шаблоны — `tools/vanessa/ASSERT-PATTERNS.md`.
- **Без пауз** `И Пауза N`: ждать события — «я жду, что в таблице … количество строк будет … в течение 10 секунд», «я жду
  закрытия окна … в течение 20 секунд».
- Шаг «в таблице … количество строк …» двигает курсор списка (Vanessa пересчитывает строки переходом по ним): перед
  командой по текущей строке после него — снова «я перехожу к строке».
- Выбор строк пользователем — в своей форме проекта, а не системным окном отметки `СписокЗначений.ПоказатьОтметкуЭлементов`:
  флажки системной формы Vanessa не отмечает.
- После «В панели разделов я выбираю …» меню функций раздела остается поверх форм — следующие шаги не находят элементы;
  такие фичи ставить последними или закрывать панель.
- Поля HTML (карты): шаг VAExtension «И я выполняю выражение '…' в текущем окне (Расширение)» выполняет код в форме
  клиента — `_ТекущееОкно.Элементы.<ПолеHTML>.Документ.defaultView.eval(…)`, результат пишут в реквизит формы и
  проверяют обычным шагом (реквизит может быть и у скрытого элемента — Vanessa значение читает). `ВызватьИсключение`
  внутри выражения шаг **не роняет**: в клиенте открывается окно ошибки, шаг — успешный, следующие шаги падают с
  непонятной причиной; поэтому проверка — только через реквизит формы и «стал равен по шаблону».
- В шаблоне «стал равен по шаблону» работает только `*`, `?` — нет. Шага «в таблице … текущая строка содержит» нет:
  строку таблицы проверяет «я перехожу к строке» с колонками-значениями (строки нет — шаг падает).
- Текст, введенный в многострочное поле, фиксирует следующее действие в форме (нажатие кнопки), а не шаг-выражение
  VAExtension: ввод в поле → выражение → «Записать» теряет введенное (Energy 0.8.28).
- Маркеры скриншотов: строка `# СКРИН: <id> | <подпись>` сразу после шага, создающего описываемое состояние.

## 5. Скриншоты для инструкций

Снимок окна Vanessa Automation или клиента тестирования 1С, который идет в инструкцию пользователя, — только **цветной PNG** (полный цвет). Серый, черно-белый и обесцвеченный кадр для такой инструкции не годится.

Снимать в цвете, без перевода в серое:

- MCP `get_window_screenshot_os` — обязательно `color_mode=color`. У инструмента значение по умолчанию `grayscale`; для инструкции его не оставлять и не подставлять вторым шагом, если цветной снимок не вышел.
- `PrintWindow` (в том числе `PW_RENDERFULLCONTENT`) или `mss` — сохранять RGB/PNG как есть, без `convert("L")` и без обесцвечивания.
- Не передавать ffmpeg фильтр `gray` / `format=gray` и ImageMagick `-colorspace Gray` (и прочие ключи grayscale).

`run_steps.py ... --shots <каталог>` делит фичи по маркерам `# СКРИН:`, прогоняет части и после каждой снимает цветной
снимок окна клиента (`get_window_screenshot_os`, `color_mode=color`); окна-диалоги 1С (отдельные окна ОС) накладываются
по центру, как на экране; `manifest.json` — id, подпись, окно, файл. Снимки делаются в том же прогоне с вайпа, что и
тесты, — в инструкции ровно те кнопки и состояния, что реально в системе. Черно-белые снимки ошибок VA для документов
не годятся. Пользователь требовал: в каждом абзаце инструкции, где названа кнопка или результат, — рисунок с ней.
В папку проекта это правило не копировать: там только ссылка на этот раздел.

## 6. Правила (из инцидентов Energy)

| Правило | Почему |
|---------|--------|
| Классический плеер `StartFeaturePlayer` запрещен — только MCP-режим | вердикты без пошагового контроля, зависания очереди |
| Лог/результаты по шагам побеждают вердикт MCP | `Success` от MCP при упавшем шаге и наоборот; после ошибки MCP `get_test_results` отдает результаты ПРОШЛОГО сценария (раннер это учитывает) |
| Нет ответа >60 с — статус в чат, таймаут = FAIL | агент молчал по 10 минут на зависшей модалке |
| Не убивать TM/TC на обычный FAIL | следующая фича сама закрывает окна (Контекст); рестарт — только после UpdateDB/CFE, правки VAParams, мертвого порта |
| Перед `connect_test_client` — клиент жив и прожил не меньше 40 с (`wait_tc_age`) | профиль без пароля: Vanessa сама стартует клиент, вход не проходит, после нескольких попыток платформа блокирует пользователя базы; после обновления базы клиент стартует дольше, и подключение через 10–15 с после запуска не проходит |
| Не слать `stop_scenario` «на всякий случай» перед каждой фичей | VA отвечает модалкой «Вызвано продолжение шагов, но не было остановки» и вешает очередь |
| VAParams — ключ `ИмяКаталогаЛогОшибок` | опечатка `КаталогВыгрузкиЛогОшибок` давала модалку «Не указано имя файла лога» на первом FAIL и вешала все фичи полтора дня |
| VAParams читается только при старте TM | после правки — `restart-vanessa.ps1` |
| После правки `.feature` — `reloadAndRun` | иначе гоняется старый текст шага из дерева VA |
| Своя пара у каждой сессии агента — на своих портах (`VANESSA_MCP_PORT`, `VANESSA_TC_PORT`); останавливать только свою (база И свои порты) | пары на разных портах в одной RDP-сессии не мешают друг другу; два комплекта на одном порту путали окна; номер RDP-сессии меняется — искать по имени пользователя/командной строке |
| Профили клиентов в VAParams — под ключами `КлиентыТестирования` и `ДанныеКлиентовТестирования` | без второго менеджер берет сохраненную таблицу профилей пользователя базы, общую для всех пар под ним: клиент подключался к порту чужой пары, Vanessa запускала клиентов без пароля |
| После своих тестов закрывать свои сеансы 1С: `close_test_client` через MCP, остальные свои процессы — kill и `cluster-sessions.ps1 -Terminate` их спящих сеансов | убитый клиент оставляет спящий сеанс до суток, они копятся и не дают UpdateDB (в Energy — 40 сеансов) |
| На TM не ставить `/DisableStartupDialogs` | тихий отказ открытия EPF (предупреждение безопасности) и обрыв сеанса |
| Остановка прогона = раннер + пара TM/TC | уже отправленный сценарий доигрывается в Vanessa без раннера |
| Прогон с привязкой к дате — не через полночь | данные создаются «сегодня», проверки после 00:00 их не находят |
| Регламентные задания базы не включать; обработчик вызывать из теста через MCP 1С (`execute_code`) | в Energy задания заблокированы на кластере, снятие запустило бы все задания ERP |
| UpdateDB мешают сеансы убитых клиентов (держатся на кластере до суток) | `scripts\1c\cluster-sessions.ps1`: мертвые (нет живого процесса) завершать с согласия пользователя; живые сеансы людей — только спросив |

## 7. Типовые неполадки

| Симптом | Причина / действие |
|---------|-------------------|
| `restart-vanessa.ps1`: «порт занят чужим процессом» | другая пара (другой проект) на этом порту — другой `VANESSA_MCP_PORT` |
| пара не готова за 240 с | `tools/vanessa/vanessa-start.log`; войти в RDP-сессию и посмотреть окна 1С (вход, предупреждение безопасности, нет `client_mcp`) |
| MCP отвечает только `infobase_info` | VA еще не открылась — подождать 1–2 мин или рестарт |
| «tool not found» сразу после рестарта | инструменты регистрируются с задержкой — `connect_main` ждет до 3 минут |
| `Файл <…feature> не существует` | путь недоступен пользователю `vanessa` (например, `%TEMP%` агента) |
| «Таблица формы с именем <…> не найдена» | имя элемента взято с подписи — смотреть `get_form_analysis` |
| модалка VA вешает очередь | ключи VAParams; лишний `stop_scenario`; закрыть окно в RDP-сессии и рестарт |
| пользователь базы заблокирован | подключались к профилю без живого клиента — разблокировать в Конфигураторе/«Пользователи», дальше только через `connect_main` |

## 8. Мобильный клиент (если проект его использует)

В Energy АРМ инспектора работал в мобильном клиенте 1С: проверка — эмулятор Android (BlueStacks) через ADB
(`127.0.0.1:5555`): снимки `adb exec-out screencap -p`, нажатия `adb shell input tap x y`, ввод — латиницей (логин
тестового пользователя `inspector`). Перед загрузкой — CheckModules с `-MobileClient` (ветки `#Если МобильныйКлиент`
тонкий клиент и Vanessa не компилируют). Ограничения МК: шрифт `kind="Absolute" height="0"` невидим; кнопки/DOM в поле
HTML не работают — только переход по относительной ссылке с разбором `ДанныеСобытия.Href`; строки-карточки таблиц
выравниваются по общей сетке колонок. Образец — `examples/energy/scripts/docs/mk_adb.sh`.

**Мобильный клиент под Vanessa (тип клиента «МобильныйКлиент», проверено в Energy 21.10.2026):** Vanessa запускает МК
через adb (`ПутьКadb` в VAParams — каталог с `adb.cmd`, который вызывает adb эмулятора только для своего устройства:
`@"…\HD-Adb.exe" -s 127.0.0.1:5555 %*`), МК входит в базу по строке `/N /P /WS "<публикация>" /TestClient -TPort …
/TestClientID id…`, но клиент тестирования для серверной базы не поднимается: в эмуляторе порт не слушает, через
кластер — «Отсутствует подходящий клиент тестирования» (в документации Vanessa — «не работает в SQL базах»). Для
серверной базы МК проверять через ADB.

## 9. Веб-клиент под Vanessa

Тесты стоит вести и в веб-клиенте: пользователи часто работают в нем, а часть ошибок видна только там (Energy, 21.10:
счетчик карты «из 0» после переключения закладок, карточка из нажатия в поле HTML открывалась фоновой вкладкой).

- **Профиль:** `ТипКлиента = "Web"`, `ПутьКИнфобазе` — адрес публикации; для серверной базы менеджер подключается к
  веб-клиенту через кластер: `ИмяКомпьютера` — сервер кластера, порт 1541 (1538 — только файловая база через
  веб-сервер). Адрес клиента — как у Vanessa: `<публикация>?TESTCLIENT&TESTCLIENTID=<имя профиля транслитом без пробелов
  и знаков>&N=<пользователь>&P=<пароль>` («Этот клиент» → `Etotklient`).
- **Браузер:** Vanessa открывает его командой `start "" "<адрес>"` — в RDP-сессии пользователя `vanessa` это может не
  сработать; надежнее запускать Edge/Chrome самим (тем же заданием, что и пару) со своим профилем
  (`--user-data-dir`), портом отладки (`--remote-debugging-port`) и **обязательно** ключами против фонового режима:
  `--disable-background-timer-throttling --disable-renderer-backgrounding --disable-backgrounding-occluded-windows
  --disable-features=CalculateNativeWinOcclusion,IntensiveWakeUpThrottling` — окно браузера перекрыто менеджером
  тестирования, и без них каждый шаг идет минутами (в Energy «жду появления элемента … 30 секунд» — 128 с против 1,8 с).
- **Повторный `connect_test_client`** к уже подключенному веб-клиенту (PID 0) вешает менеджер — подключаться, только
  если профиль не подключен (`manage_test_client_profiles get_list`).
- **client_mcp** (MCP-сервер Vanessa в базе): в версии 0.6.5 модуль `Мсп_ИнструментИнфоИБКлиент` обращается к
  `Метаданные` везде, кроме тонкого клиента, — в веб-клиенте модальное «Переменная не определена (Метаданные)» на
  каждой форме, шаги висят. Исправление — условие `#Если ТонкийКлиент Или ВебКлиент Тогда` (три места); с `Или
  МобильныйКлиент` платформа это расширение не применяет. Образец — `examples/energy/scripts/1c/install-client-mcp-web.ps1`.
- **Шаги VAExtension «я выполняю выражение '…' в текущем окне (Расширение)»** в веб-клиенте не работают («Оператор
  Выполнить в веб-клиенте не поддерживается»). Образец замены — `examples/energy/scripts/pmi/va_web_steps.py`: фича
  делится на части по таким шагам, JavaScript поля HTML выполняется в странице через порт отладки (Playwright),
  присваивание реквизиту и следующие проверки «стал равен» считаются в раннере, отбор динамического списка — элемент в
  сохраненных пользовательских настройках списка (`ХранилищеСистемныхНастроек`, ключ
  `<форма списка>.Список/ТекущиеПользовательскиеНастройки`, идентификатор пользовательского отбора
  `dfcece9d-5077-440b-b6b3-45a5cb4538eb`) с возвратом в конце сценария; код 1С формы — переписать фичу.
- **Поле HTML в веб-клиенте** (ошибки продукта, видные только в вебе): новый HTML поля веб-клиент пишет в тот же
  документ окна - глобальные переменные прежнего документа остаются (скрипт, пропускающий запуск по флагу окна,
  остается на старом элементе нулевого размера); функция JavaScript, прочитанная свойством окна из кода 1С, приходит
  `Неопределено` - проверять через `eval("typeof ...")`, вызов метода работает; форма, открытая прямо из обработчика
  нажатия в поле HTML, остается фоновой вкладкой - открывать обработчиком ожидания после нажатия; поле скрытой
  закладки - нулевого размера (карты сверяют размер и не шлют на сервер вырожденное окно).
- **Фичи для обоих клиентов:** элементы скрытой закладки веб-клиент не показывает — сначала «я перехожу к закладке»;
  «открылось окно» — шаблоном, которому не отвечает сам список; строку списка выбирать явно, не «текущую»; «форма
  изменена» в вебе — « *» в заголовке активного окна; шаги только для веба — строкой `# веб+ <шаг>`.
