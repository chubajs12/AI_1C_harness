# Как я работаю (агент проекта Energy, Claude Code)

Описание реального процесса, по которому вел проект ОЭК ЭнергоКомплекс (1С:ERP Энергетика 2.5 + расширение `ОЭК_ШСЮ`)
с 20.09 по 07.10.2026: что настроено, в каком порядке делается работа, почему так. Правила в сжатом виде — `AGENTS.md`;
здесь — объяснение и практика. Конфигурация вашего проекта другая: переносится процесс, а не предметная область.

## 1. Окружение

Одна машина Windows Server (16 CPU, 64 ГБ), на ней:

| Что | Как устроено |
|-----|--------------|
| Кластер 1С | `Main_claster` :1540, платформа 8.3.27.1936; базы проекта на MS SQL |
| Рабочая база | клиент-серверная, общая для людей и агентов; на ней расширение, которое дорабатываем |
| Агент | Claude Code (десктоп-приложение, вкладка Code), рабочая папка — каталог настроек проекта |
| Каталог настроек | `F:\AI_Claude\<проект>`: `CLAUDE.md` (правила), `.mcp.json`, `.claude\` (skills, агенты), `scripts\`, `docs\`, `tasks\`, `indexes\` |
| Каталог сырцов | `F:\AI_Claude\<проект>_src`: `conf` (выгрузка основной конфигурации), `ext` (выгрузка расширения), `build` (CFE, обработки) |
| MCP | общие контейнеры Docker (граф, справка, синтаксис, БСП, формы, шаблоны, стандарты) + свой индексатор кода проекта |
| MCP 1С | HTTP-сервис расширения `MCP_Сервер` в базе, опубликован на IIS (127.0.0.1, Basic): код и запросы в живой базе (до 16.10.2026 — OneBridge, толстый клиент с обработкой) |
| Vanessa | TestManager + TestClient в отдельной RDP-сессии Windows-пользователя `vanessa`; MCP Vanessa по HTTP |
| Git | локальные репозитории (настройки, сырцы расширения), без remote |

Параллельно на машине работали другие проекты (Долея, Роствипласт, Миракс) и до десятка сессий агента — отсюда
правила про общие ресурсы.

## 2. Ход любой задачи

1. **Постановка.** Пользователь назвал задачу — создаю `tasks/YYYY-MM-DD-кратко/brief.md`: дословный запрос, решение,
   приемка. Не назвал — спрашиваю, новая задача или продолжение (показываю `tasks/`).
2. **Разведка через MCP.** Объекты, реквизиты, формы, кто вызывает метод, кто пишет в регистр, права ролей — только через
   индексатор кода и граф (не через чтение XML). Текущие данные базы — через MCP 1С (`execute_query`). Справка по
   платформе — `1c-docs-mcp`, готовые механизмы — `1c-ssl-mcp`.
3. **План.** Для сложной задачи — `tz.md` с чек-листом приемки и тестами; разбивка на маленькие проверяемые батчи.
4. **Если нужен новый объект метаданных** — создаю сам навыком comol `1c-metadata-manage` (с 20.10.2026; до этого —
   стоп и описание для пользователя), проверяю XML (`meta-validate` / `cfe-validate`) и UUID. Без набора comol — пишу
   пользователю, что создать в Конфигураторе (вид, имя, тип, свойства, место), жду, затем выгружаю свежее расширение.
5. **Правка** модулей и форм в `ext` (XML выгрузки). Новые процедуры/перехватчики — с префиксом проекта; код по
   стандартам (области, описания методов, без «ё»).
6. **Гейты** (AGENTS.md п. 3): синтаксис каждого модуля, тексты запросов на живой базе, валидация форм, UUID.
7. **Версия:** bump в `Configuration.xml` и `VERSION`.
8. **Деплой:** Full Load → CheckModules (тонкий, веб, сервер, мобильный) → UpdateDB → выгрузка CFE (прошлый — в `old/`).
9. **Тест:** вайп тестовых данных → микрокомандный прогон (подготовка через MCP 1С, фичи Vanessa по одной, проверки
   данных MCP 1С) → новая/обновленная фича под изменение → полный прогон блока до fail=0.
10. **Разбор соответствия**: каждое требование — выполнено / нет, с доказательством. Не выполнено — снова к шагу 5.
11. **Git:** коммит + тег версии в репозитории сырцов (и в репозитории настроек, если менялись скрипты/правила).
12. **Отчет:** что сделано, ссылки на CFE и документы, итоги тестов таблицей, риски, что дальше. Запись в `log.md`.

## 3. Как держится контекст между сессиями

- Все, что должно пережить сессию, — на диске: `brief.md` (что и зачем), `tz.md` (план и приемка), `log.md` (что
  сделано, решения, следующий шаг). Новая сессия или сжатие контекста — первым делом читается задача.
- Правила, выученные на ошибках, сразу записываются в `CLAUDE.md`/`AGENTS.md` (раздел по теме) и строкой в
  `docs/changelog.md` с bump версии настроек. Устные договоренности, которых нет на диске, — не существуют.
- Пользовательские предпочтения (язык, формат ссылок, как давать код для переноса) — в правилах, а не в памяти чата.

## 4. Как я общаюсь с пользователем

- По-русски; коротко: что сделано, что идет, что нужно от пользователя.
- На долгих операциях (загрузка, UpdateDB, прогон тестов, индексация) — статус не реже раза в 5 минут; долгие команды
  запускаются фоном инструмента агента, их вывод читается по ходу.
- Файлы — markdown-ссылками; код для переноса в Конфигуратор — целыми процедурами; списки объектов — по алфавиту.
- Вопрос пользователю — только когда решение действительно его (изменение типовой, загрузка в общую базу, удаление
  данных, остановка чужого; новый объект метаданных — если набора comol нет). Технические развилки решаю сам и пишу, что выбрал.
- Ничего не утверждаю без проверки: «загружено» — после лога Конфигуратора и проверки версии расширения в базе через
  MCP 1С; «тесты зеленые» — после таблицы результатов по шагам.

## 5. Что я настраивал (хронология в `06_Как_ставились_правила.md`)

- Перенос харнеса из Cursor в Claude Code: правила (`CLAUDE.md` вместо ~30 файлов `.mdc`), 50 skills по 1С
  (формы, СКД, макеты, расширения, обработки, выгрузка/загрузка), агент-исполнитель для фоновых задач.
- 20.10.2026: базовый набор правил comol/ai_rules_1c (как в соседних проектах) под нашими правилами; агент сам
  создает объекты метаданных навыком `1c-metadata-manage`.
- MCP: подключение общих серверов, свой индексатор кода (bsl-indexer в Docker), переход на общий граф метаданных для
  всех проектов, помощник `mcp_http.py` на случай, когда коннектор сессии не поднялся.
- Живая база: сначала OneBridge (запуск/остановка только своего процесса, клиент `ob_client.py`), с 16.10.2026 — MCP 1С
  (расширения без безопасного режима через служебную обработку, публикация IIS со своим пулом, остановка пула перед
  UpdateDB, клиент `mcp1c.py`); BSL-скрипты подготовки, вайпа и проверок — те же.
- Vanessa: отдельная RDP-сессия, запуск пары через задачу планировщика (без пароля), перезапуск только своих процессов,
  раннеры фич по одной, микрокомандные прогоны со списком шагов, скриншоты по маркерам для инструкций.
- Сборка: обертки Конфигуратора (Full Load, UpdateDB отдельно, CheckModules, DumpCfg), автосортировка состава
  расширения, проверка UUID, компиляция текстов запросов на живой базе.
- Git: локальные репозитории, восстановление истории версий из сохраненных CFE, теги на каждую версию.
- Выпуск в боевую: список изменений от последней боевой, трехстороннее сравнение, сверка CFE боевой после переноса.
- Документация: инструкции пользователя (Word со скриншотами из прогонов Vanessa), ПМИ, ТЗ по факту, BPMN.

## 6. Чего я не делаю

- Не меняю типовую конфигурацию напрямую; объекты метаданных не создаю мимо навыка `1c-metadata-manage` (руками в XML,
  копированием каталога объекта).
- Не гружу расширение частично, не совмещаю Load и UpdateDB, не собираю CFE мимо Конфигуратора.
- Не трогаю чужие процессы 1С, чужие контейнеры, чужие проекты и каталоги другого агента.
- Не удаляю контейнеры и данные без просьбы; не пушу в удаленные репозитории; не кладу секреты в git и в чат.
- Не продолжаю «по памяти», когда MCP мертв, — говорю об этом и жду.
