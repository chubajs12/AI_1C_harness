# Цикл доработки конфигурации в расширении

Порядок, по которому в Energy выпущено ~90 версий расширения `ОЭК_ШСЮ` (0.6.x → 0.8.26) на ERP. Для вашей
конфигурации порядок тот же; команды — скрипты комплекта; сроки (выгрузка, индексация) зависят от размера конфигурации.

## 0. Каталоги и репозитории

```
F:\AI_1C\harness\          общее: AGENTS.md, rules\, skills\, scripts\, tools\, mcp\, docs\
F:\AI_1C\projects\<имя>\   свое: PROJECT.md, config\project.env.local, tasks\, indexes\
F:\AI_1C\projects\<имя>_src\conf\    выгрузка основной конфигурации (вне git)
F:\AI_1C\projects\<имя>_src\ext\     выгрузка расширения — то, что правим (git)
F:\AI_1C\projects\<имя>_src\build\   CFE и внешние обработки
F:\AI_1C\projects\<имя>_src\VERSION  версия сырцов расширения
```

Git (только локально, без remote):

```powershell
git -C <SRC_ROOT> init; git -C <SRC_ROOT> config core.autocrlf false
# .gitignore сырцов: /conf/  /build/**/*.cfe  /build/**/*.epf  /build/**/old/  **/.code-index/
git -C <SRC_ROOT> -c user.name=<GIT_AUTHOR> -c user.email=<GIT_EMAIL> commit -m "..."
git -C <SRC_ROOT> -c user.name=<GIT_AUTHOR> -c user.email=<GIT_EMAIL> tag -a v0.1.1 -m "..."
```

## 1. Выгрузка

```powershell
scripts\1c\designer.ps1 -Action Dump -Target conf    # основная конфигурация (ERP — десятки минут, после — индексация часы)
scripts\1c\designer.ps1 -Action Dump                 # расширение -> EXT_DIR
scripts\mcp\code-index\reindex.ps1 -Repos ext,conf   # индекс подхватит изменения
```

«Выгрузить свежий» — всегда Dump из базы сейчас. Если в базе расширение новее дерева (правили люди) — сначала выгрузить
и закоммитить «как есть», потом начинать свои правки: иначе Full Load затрет чужие изменения.

## 2. Анализ (MCP)

- Где менять: индексатор (`search_function`, `grep_code`, `get_object_structure`), граф (`get_object_dossier`).
- Кого заденет: `get_callers`, `find_references`, граф `trace_impact`, `find_usages_of_object`, `get_register_writers`.
- Что уже умеет типовая/БСП: `1c-ssl-mcp` `ssl_search`.
- Нужен объект/реквизит, которого нет, — **стоп, сообщение пользователю** (что, где, тип, свойства), ждать, после —
  Dump расширения.

## 3. Правка

- Модули и формы в `EXT_DIR` (XML-выгрузка Конфигуратора, формат Hierarchical). Перехват типового — в заимствованном
  объекте (`&Перед`, `&После`, `&Вместо`, `&ИзменениеИКонтроль`), новые процедуры — с `<PREFIX>`; директива
  перехватчика модуля формы совпадает с `callType` в `Form.xml`.
- Формы: правка `Form.xml` (skills `form-edit`, `form-info`, `form-patterns`; большие формы — из JSON-спецификации
  `form-compile`), каждое `Элементы.<Имя>` модуля должно быть в форме (иначе ошибка только в рантайме).
- Без «ё» в коде BSL и XML (в `//` / `/* */` комментариях BSL — можно, `check-yo.py`); области и описания методов
  (AGENTS.md п. 4); строки ≤ 120.

## 4. Гейты до загрузки

```powershell
python scripts\mcp\syntaxcheck_file.py <EXT_DIR>\...\Module.bsl          # каждый измененный модуль
python scripts\1c\check-query-texts.py <модули.bsl>                        # тексты запросов на живой базе (MCP 1С)
python scripts\mcp\validate_form_file.py <EXT_DIR>\...\Form.xml           # каждая измененная форма
python scripts\1c\uuid-check.py <EXT_DIR>                                   # UUID (его же вызывает designer.ps1)
python scripts\1c\check-yo.py <EXT_DIR>                                     # «ё» (его же вызывает designer.ps1)
python scripts\1c\sort-configuration-objects.py <EXT_DIR> --check           # состав по алфавиту (designer.ps1 сортирует сам)
```

## 5. Версия

Bump SemVer: `<Version>` в `EXT_DIR\Configuration.xml` (сохранить CRLF и BOM файла — в Energy с 0.8.4 по 0.8.6 файл
стал LF и дерево разошлось с выгрузкой платформы) + `<SRC_ROOT>\VERSION`. Patch — исправление, minor — новый механизм /
реквизиты, major — смена концепции.

## 6. Деплой (база проекта, монопольно)

```powershell
scripts\1c\designer.ps1 -Action Load          # Full Load расширения (сортировка состава + UUID перед загрузкой)
scripts\1c\check-modules.ps1                  # CheckModules: тонкий, веб, сервер, МОБИЛЬНЫЙ клиент
scripts\1c\designer.ps1 -Action UpdateDB      # отдельной командой, без лимита
scripts\1c\dump-cfe.ps1                       # CFE из базы -> build\...\<PROJECT>_<EXT>_vX_Y_Z.cfe, прошлый -> old\
python scripts\mcp1c\mcp1c.py tests\smoke\bsl\env_check.bsl         # версия расширения в базе = новая, активно
```

- UpdateDB нужен монопольный доступ: `designer.ps1` сам останавливает пул IIS публикации MCP 1С (с завершением сеансов
  публикации) и запускает после (`scripts\mcp1c\mcp-pool.ps1`). Мешают и сеансы убитых клиентов Vanessa: кластер
  держит их до суток. `scripts\1c\cluster-sessions.ps1` — сеансы базы
  (rac через временный RAS) и живые процессы клиентов; мертвые (нет процесса с тем же временем начала) завершить
  `-Terminate <номера>` с согласия пользователя; живые сеансы людей — только спросив.
- После UpdateDB/CFE — `scripts\vanessa\restart-vanessa.ps1` (клиенты тестирования должны увидеть новую версию).
- Проверить CFE: разобрать во временной файловой базе и сверить с `EXT_DIR` (образец —
  `examples/energy/scripts/git/backfill_versions.py`: `ensure_ib` + `dump_binary`).

## 7. Тест

1. Фича под изменение (новая или обновленная) + проверка данных MCP 1С (`tests/templates/check_template.bsl`).
2. Прогон затронутого блока: `python scripts\vanessa\run_steps.py tests\<блок>\steps.json` (вайп первым шагом).
3. FAIL продукта → к п. 3; FAIL фичи → поправить фичу, прогнать только ее.
4. До fail=0. Итоговая таблица — в `log.md` задачи и в ответ пользователю.

## 8. Закрытие версии

- Разбор соответствия требованиям (каждый пункт — выполнено/нет, доказательство).
- `git commit` + `git tag -a vX.Y.Z` в `<SRC_ROOT>` (и в `<PROJECT_ROOT>`, если менялись скрипты/правила — свой трек
  версий, строка в `docs/changelog.md`).
- Ответ: что сделано, markdown-ссылка на CFE, итоги тестов, риски, что дальше; запись в `log.md`.
- Если пользователь хранит историю поставок в отдельной папке (в Energy — **корень диска `G:\`**, только `.cfe`, имя
  `energy_OEK_SHSYU_vX_Y_Z.cfe`) — копия CFE туда по правилам ниже.

### 8.1. DumpCfg, отдача пользователю и `G:\` (Energy / ОЭК_ШСЮ)

Канон: `rules/cfe-version-g-drive.md`.

1. **Каждая новая отдача пользователю** и **каждая копия на `G:\`** = **SemVer patch +1** в `Configuration.xml`, новый
   `DumpCfg`, новое имя файла. **Запрещено** перезаписывать на `G:\` уже отданный `.cfe` **того же имени версии**
   другим содержимым (`Copy-Item -Force` без проверки).
2. **Без новой версии** допустимо только если боевая CFE от пользователя **байт-в-байт** совпадает с последней нашей
   отданной (на `G:\`, в `build/OEK_SHSYU/` или в задаче): baseline/тег, сверка — **без** bump и **без** DumpCfg.
3. Копирование: `scripts/1c/copy-cfe-release.ps1` или `dump-oek-shsyu-cfe.ps1 -CopyToG` (energy). Харнес:
   `dump-cfe.ps1` → `build/`; на `G:\` — только через safe-copy.
4. На `G:\` — **только** `.cfe`; списки захвата, отчёты, md — в `tasks/<id>/` проекта energy.

## 9. Выпуск в боевую (боевую ведут и другие разработчики)

Боевая база на хранилище, агент ее не трогает. Основной порядок (образцы скриптов — `examples/energy/scripts/git/`):

1. **Свежая копия боевой.** Пользователь выгружает CFE боевой; агент кладет ее снимком в git (коммит вне основной ветки,
   тег `prod-YYYY-MM-DD-HHMM`) и делает трехстороннее сравнение (прошлая боевая — наша — свежая боевая,
   `three_way_prod.py`): «двойные» изменения (и мы, и боевая меняли одно место) и изменения только боевой.
2. **Агент дорабатывает нашу версию до боевой и дает дельту**: изменения только боевой — к себе как есть, двойные —
   объединяет сам (ничего чужого не терять), ищет обращения нашего кода к тому, что боевая переименовала или удалила.
   Новая версия, полный прогон, CFE и дельта к свежей боевой: что захватить в хранилище, свойства, процедуры целиком,
   тексты запросов (`changes_since_prod.py <снимок> <наша> <файл.md>` + тексты). Пользователь переносит ровно дельту —
   CFE целиком в боевую не загружается; после переноса боевая должна совпасть с нашей версией.
3. **Проверка после переноса** (`verify_prod_cfe.py <cfe боевой> <снимок шага 1> <наша> --ours-cfe <наша.cfe>`): обе CFE
   разбираются и сравниваются байт в байт, плюс сверка со снимком шага 1 — ничего из боевой не пропало. Только при 0
   расхождений CFE боевой принимается как основная (`ext` из нее, bump, коммит, тег). Чужие изменения после снимка —
   новый шаг 1.

Зачем так (Energy, 29.09): при ручном переносе общий модуль, который меняли и мы, и другой разработчик, взяли целиком
нашим — пропала чужая функция, а сверка после переноса проверяла только наше.

## 10. Внешние обработки

Skills `epf-init`, `epf-build`, `epf-dump`, `epf-validate`, `epf-bsp-init` (для «Дополнительных отчетов и обработок»
БСП). Имя файла `<PROJECT>_<Имя>_vX_Y_Z.epf`, своя версия (`build\<Имя>\VERSION`, первая публикация `1.0.1`), прошлые —
`old\`. Сборка — только Конфигуратором (`/LoadExternalDataProcessorOrReportFromFiles`), не упаковщиками.
